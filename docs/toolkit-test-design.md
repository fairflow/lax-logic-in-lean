# Testing the prover toolkit cleanly — a proposal

**Status:** proposal, for Matthew's decision. Nothing here is built.
**Written:** 2026-08-30, after running the four `LaxLogic/ToolkitTest/Challenge`
files end to end with `prove-lemma-inloop`.

## 1. The problem: prefix truncation guarantees contamination

The challenge set is generated by **prefix truncation** — the source file up to
the target statement, with the proof replaced by `sorry`. That method has a
property which no amount of instruction-not-to-peek can remove:

> Everything the ground-truth proof used is, by construction, above the cut.

The agent is told not to open the original file. It does not need to. The
challenge file *is* a walkthrough ending at the answer, and reading it is
mandatory, not optional.

### What that cost, measured on the existing four

All four closed on the first `check`, which sounds like a result and is not
one. Per file:

| file | ingredients outside the challenge file | verdict |
|---|---|---|
| `conservativity_prop.lean` | none — its ground truth is *in* `conservativity.lean* | **void**: the answer was in a file the task required reading |
| `conservativity.lean` | none | **near-void**: `conservativity_prop`, an isomorphic sibling, sits proved 60 lines above the goal — same 13-case induction, same case order, same `laxElim` insight |
| `focalization.lean` | none — `sound`, `focalizeD`, `map_unNeg_negOf`, `unNeg_negOf_isIPL` all in the prefix | weak |
| `pfree_trans.lean` | `LJF.PFreeP`, `LJF.PFreeN` (in `LJF.lean`) | **the only real test** |

Retrieval was used four times across the set and did real work **once** —
on `pfree_trans`, and for exactly the reason that makes it the only valid
member: what the proof needed was not in the file. That is the whole signal
from four files, and it is the design principle in one line.

Two further observations, worth keeping:

- The file header states *"Ground truth exists (14-line proof)"* and names the
  source file and line. That is itself a hint (a short proof means: do not
  attempt anything structural) and an invitation.
- `conservativity` and `conservativity_prop` should never both have been in the
  set. A target whose proof is structurally isomorphic to a sibling in the same
  module tests nothing once the sibling is visible.

### One thing that already works, and should be kept deliberately

The index stores `signature` + `docstring` for a `theorem` and **no proof
body**, so `search` cannot leak a ground truth for a theorem target. It *does*
store full bodies for `def`s. So:

- theorem targets are safe under retrieval;
- **`def` targets are not** — a sorried `def` would have its answer served by
  `search`. Do not put one in a challenge set.

## 2. What a clean test requires

1. **The ingredients live outside the challenge file.** Non-negotiable; it is
   the only property that distinguished the one valid member.
2. **The challenge file is short enough to read in full without learning
   anything** — imports, statement, `sorry`.
3. **No isomorphic sibling is visible.** Reject a target whose proof is a
   near-duplicate of another declaration in the same module.
4. **The target is a `theorem`, not a `def`** (§1).
5. **The challenge files are not in the index.** They are currently indexed
   alongside the originals they were copied from: 99 duplicate entries, and in
   one query 9 of the top 16 slots went to 3 distinct declarations.
6. **The header is blind** — no line count, no source location, no difficulty.
7. **Something is recorded.** At present the test produces a narrative and no
   number.

## 3. Measured facts about retrieval, for whoever builds this

From ablations over `prover-toolkit/leansearch/index.jsonl` (2903 entries).
Retrieval is lexical BM25 over `name + signature + docstring + module`; no
embeddings, no stemming, no type-directed search.

**Engine, systematic.** `KIND_BOOST` rates `notation` 2.2, `inductive` 1.9,
`def` 1.25, `theorem`/`lemma` **1.0** — the floor. 59% of the corpus is
theorems and lemmas, and a lemma-to-apply is the commonest need in a proof
loop. On 267 four-word queries for documented theorem targets, with the
target's own name-tokens removed:

| | top-1 | top-10 |
|---|---|---|
| as shipped | 42.7% | 86.5% |
| `KIND_BOOST` neutralised | **51.7%** | **93.6%** |

Given the full docstring sentence instead of four words: 72% / 98%. The engine
is good when the query shares surface vocabulary with the docstring, and weak
when the query is short. A `--kind theorem` filter, or making the boost
query-conditional, is the single highest-yield fix.

**Engine, sporadic.** No stemming. Corpus-wide, morphological perturbation cost
nothing measurable — the rest of the sentence rescues it. But when the query is
short and the one discriminating word is off by a suffix it is decisive:
`…Inv soundness back to natural deduction…` ranked its target 23rd;
`…Inv sound…` ranked it 2nd.

**Index construction.** Excluding `ToolkitTest` gains ~0.4pt corpus-wide but 6
ranks on the affected query, and removes a real leak risk for `def` targets.

**Corpus.** Docstring coverage is 68.2% overall: `structure` 93%, `def` 87%,
`theorem` 57%, `lemma` **4.8%** (1 of 21). 43% of theorems and lemmas offer
nothing but a signature to match on, and are reachable only by a query already
containing their identifiers.

## 4. The proposal: hole-punching, not truncation

Replace prefix truncation with **hole-punching**, and move the punched module
out of the challenge file.

For a target theorem `T` in module `M`:

1. Build `M_punched` — `M` verbatim with **only `T`'s proof** removed and `T`
   itself deleted (not `sorry`ed; it must not be in scope). Everything else in
   `M` survives, including declarations that came *after* `T`.
2. The challenge file is then:

   ```lean
   import <M's own imports>
   import M_punched
   open <namespaces>

   theorem T <verbatim statement> := by
     sorry
   ```

   Four lines the agent can read in full while learning nothing.
3. Index `M_punched` and the rest of the development; **exclude the challenge
   file**.
4. Reject `T` if some other declaration in `M` has high token overlap with
   `T`'s proof (the `conservativity` / `conservativity_prop` trap).

This is strictly better than truncation on every count in §2, and it reuses the
existing extractor: hole-punching is truncation plus a tail, and the tail is
the part that makes it a test rather than a walkthrough.

**Cheaper variant, if that is too much:** keep truncation but require, as an
acceptance criterion on the generated file, that **at least one lemma the
ground-truth proof cites is absent from the prefix**. That is a one-line filter
over the extractor's output and it would have rejected three of the four
existing files. It does not fix the isomorphic-sibling trap.

**Variant that needs no extractor work at all:** take targets from commits
*later* than the one the index was built from. The ground truth then cannot be
in the corpus. It still needs hole-punching to keep it out of the working tree.

## 5. What to measure

Per lemma, recorded automatically by the harness rather than narrated:

- attempts to the first green `check`, and whether it ever went green;
- number of `search` calls, and — the interesting one — **whether any search
  result was cited in the proof that finally worked**;
- axioms, against the baseline of the ground-truth proof;
- wall-clock and tokens.

And the one experiment the toolkit's own README lists as *not established*
("whether the corpus index helps — it is *used*, but never ablated"):

> **Run every lemma twice: once with the server up, once with it down.**

With the server down the skill degrades to `grep` plus whole-file reading. That
is a cheap, clean A/B, and on this session's evidence the honest prior is that
the index will show no benefit on well-documented targets in the same file and
a large benefit on targets whose supporting lemmas are elsewhere — which is
precisely the split §4 is designed to create.

## 6. Staging

1. Exclude `ToolkitTest` from the index roots. One line. *(Done — see the
   commit that added this file; revert freely.)*
2. Blind the challenge headers, and drop `conservativity_prop` from the set.
3. Add the acceptance filter of §4 ("a cited lemma must be absent") to the
   extractor, and regenerate. This alone converts the set from decorative to
   informative.
4. Hole-punching proper, plus the harness metrics of §5.
5. The retrieval ablation.

Steps 1–3 are an afternoon. Step 4 is the real work and is where the extractor
would need to learn to emit two files instead of one.

## 7. What this does not address

Whether the toolkit helps on goals that are *open* rather than merely
*re-derived*. A challenge set built from proved lemmas measures re-derivation
under retrieval, which is a genuine and testable thing, but it is not the
question of whether the loop can advance a research problem. `NewClaims.lean`
gestures at that and has the opposite defect: invented statements with no
ground truth, so a failure cannot be distinguished from a false statement.
